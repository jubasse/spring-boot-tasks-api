# AGENTS.md

Guidance for coding agents working in this repository (Claude Code reads it through `CLAUDE.md`).

**Where things are:** `docs/cartography.md` maps the packages, the project's own annotations and test helpers, and the registries a new feature must extend. Read it before searching the code for a utility, and before writing one: it may already exist.

## Stack

Spring Boot 4.1 REST API (Java 25, Maven wrapper), PostgreSQL 18, S3-compatible object storage for media, RabbitMQ for background work. Spring Data JPA (Hibernate 7), Spring AMQP, Liquibase, Spring Security (stateless OAuth2 resource server, self-issued HS256 JWTs), Lombok, springdoc-openapi. MapStruct is on the classpath but unused: DTOs are records built from entities by their constructor (`new TaskResponseDto(task)`).

## Commands

```bash
./mvnw compile                                  # build (runs Lombok + MapStruct + config annotation processors)
./mvnw spring-boot:run                          # run; spring-boot-docker-compose starts compose.yaml (postgres, mailpit, rustfs, clamav, rabbitmq)
docker compose up -d                            # needed once after compose.yaml gains a service: see the note below
./mvnw spring-boot:test-run                     # run with a Testcontainers postgres (TestTasksApplication)
./mvnw test                                     # all tests (needs Docker, Testcontainers)
./mvnw test -Dtest=TasksApplicationTests#contextLoads   # a single test
```

Note: `spring-boot-docker-compose` skips `docker compose up` if some project services already run: a service added to `compose.yaml` later (`rustfs`, `clamav`, `rabbitmq`) needs one manual `docker compose up -d`.

Tests need no `.env`: `src/test/resources/config/application.yaml`, loaded over the main `application.yaml`, gives a test-only JWT secret. `./mvnw test` also writes a JaCoCo report to `target/site/jacoco/index.html` (raw numbers in `jacoco.csv`).

Local config: `.env` (git-ignored; copy `.env.example`). `compose.yaml` reads its `POSTGRES_*`; `application.yaml` imports it (`spring.config.import: optional:file:.env[.properties]`) to resolve `security.jwt.secret: ${JWT_SECRET}`. `JWT_SECRET`: Base64 decoding to at least 32 bytes (`openssl rand -base64 32`), or `JwtConfiguration` fails startup. The import path is relative: run the app from the project root.

Spring Boot 4 uses **Jackson 3** (`tools.jackson.*`): inject `JsonMapper`, not `com.fasterxml…ObjectMapper`, because no Jackson 2 bean exists. Jackson 2 comes only through Hibernate, for JSON columns, hence `TaskEvent.payload` is a `Map<String, Object>`, not a `JsonNode`.

## Database / migrations

- `spring.jpa.hibernate.ddl-auto: validate`: every entity change needs a Liquibase changeset, or startup fails.
- Changesets: YAML in `src/main/resources/db/changelog/changes/`, named `NNN-name.yaml`, loaded by `includeAll`. Existing ones were generated from entities by `liquibase-maven-plugin` + the `liquibase-hibernate7` diff extension (configured in `pom.xml`; `src/main/resources/liquibase.properties` points at the local DB, without password: pass `-Dliquibase.password=...`).
- Primary keys: UUIDv7 generated by Postgres (`@Generated` + `@ColumnDefault("uuidv7()")`, needs Postgres 18). Don't assign IDs in Java.
- Constraint names: `<table>_<column>UQ`, `<table>_<column>FK`, `<table>PK`.
- `AuditableEntity` (base of `User` and `Task`): `created_at`/`updated_at` by Spring Data auditing; **soft delete** by Hibernate `@SoftDelete` on `deleted_at`: `repository.delete()` sets it, and every query filters soft-deleted rows automatically.
- Unique constraints (`users_emailUQ`, `tasks_referenceUQ`) also cover **soft-deleted rows**: a deleted user's email or task's reference stays taken. JPQL and derived queries cannot see those rows (`@SoftDelete`), so an existence check guarding a unique constraint must be native (`existsByEmailIncludingDeleted`, `existsByReferenceIncludingDeleted`), or the check passes and the insert fails. `ApiExceptionHandler` maps any remaining `DataIntegrityViolationException` (e.g. two concurrent inserts) to 409.

Generate a changeset from entity changes against a database with every migration applied (a throwaway container works):
```bash
./mvnw liquibase:diff \
  -Dliquibase.url=jdbc:postgresql://localhost:5432/tasks -Dliquibase.username=... -Dliquibase.password=... \
  "-Dliquibase.referenceUrl=hibernate:spring:io.julienmetral.tasks?dialect=org.hibernate.dialect.PostgreSQLDialect&hibernate.physical_naming_strategy=org.hibernate.boot.model.naming.PhysicalNamingStrategySnakeCaseImpl" \
  -Dliquibase.diffChangeLogFile=src/main/resources/db/changelog/changes/NNN-name.yaml
```
Then review the generated file; give its changesets readable `id`s and a real `author`.

Warning: compile first: the diff reads entities from `target/classes`. It compares indexes and foreign keys by table and columns, not name: a renamed constraint or index is not reported (checked on 2026-09-27), so check names against the convention by hand. A missing constraint or changed column is reported.

Passwords: Argon2id (`SecurityConfiguration.passwordEncoder`, Bouncy Castle implementation). BCrypt is registered only to verify legacy hashes, upgraded to Argon2id by `DatabaseUserDetailsService.updatePassword` on the next successful login. `{noop}` is not registered: tests storing users directly hash with the `PasswordEncoder` bean.

## Architecture

Package-by-feature under `io.julienmetral.tasks`, same sub-packages in each feature (`controllers`, `services`, `repositories`, `entities`, `dtos`, `exceptions`, `security`):

- `identity`: users, login, JWT and refresh tokens, email verification, user-level authorization.
- `task`: tasks, event log, comments (see Task comments), attachments (`/api/v1/tasks/{id}/attachments`: added by an admin or the assignee, listed by any active user, removed by an admin or the uploader; additions and removals are history events).
- `export`: Spring Batch CSV exports of tasks and users, and each account's personal data export (see Exports).
- `mail`: cross-cutting mail service (see Mail).
- `messaging`: the outbox every RabbitMQ message goes through (see Outbox).
- `media`: stored files and metadata (see Media storage); sub-packages `model` (entities, enums, value records), `services`, `repositories`, `health`, `exceptions`.
- `config`: application-wide technical configuration, such as storage drivers.
- `notification`: task email notifications, per-user settings, webhook endpoints (see Webhooks).
  - **Shared rules:** `notification.services.TaskNotificationPublisher` turns task events into one `notification.events.TaskNotificationCreated` per recipient (never about their own action, active accounts only), for webhooks and notification streams. Emails keep their own listener, rules and switches.
  - **Settings:** `GET`/`PUT /api/v1/users/{id}/notification-settings`, user or admin: one switch per task event plus `taskCommented`, `taskMentioned`, `taskDueSoon`, `taskOverdue`; no stored row -> `NotificationSettings.defaults` (all enabled).
  - **Emails:** domain events from `TaskService` and `TaskCommentService` (`task.events.TaskAssigned`, `TaskUnassigned`, `TaskCancelled`, `TaskDeleted`, `TaskCommentAdded`, `UsersMentionedInComment`) and `TaskReminderService` (`TaskDueSoon`, `TaskOverdue`) become emails in `notification.mail.TaskNotificationSender`: only to the concerned assignee (or mentioned user), never about their own action, only while their account is active and the matching switch is on. The `task` package never depends on `notification`.
- `realtime`: events relayed to every instance, notification streams, task rooms (see Real-time events).
- `shared`: auditable base entity, global `ApiExceptionHandler` (`@RestControllerAdvice` returning `ProblemDetail`), reusable security annotations.

Controllers are served under `/api/v1/...` but declare paths without it (`@RequestMapping("/tasks")`): `config.ApiVersioningConfiguration` prefixes application controllers with `/api/v{version}`, and Spring Framework 7 reads the version from that segment (supported: `1`). `PathVersionParser` accepts only the spelling `v1`: Spring's default parser also served `/api/v1.0/` and `/api/v01/` as version 1, where security rules written for `/api/v1/` did not apply, so a disabled account listed tasks. Security rules on API paths match every version (`/api/*/...`). A new version of one operation: another method mapped with `version = "2"`, once `2` is supported; unchanged operations answer both. Warning: a controller writing `/api/v1` itself ends up under `/api/v{version}/api/v1`. Services own transactions and return entities; controllers wrap them in response DTOs.

### Auth flow

1. `POST /api/v1/auth/login` -> `AuthService` authenticates via `DaoAuthenticationProvider`/`DatabaseUserDetailsService` (`UserRole` -> `ROLE_<name>` authorities); `JwtService` issues a token with claims `uid` (user UUID) and `roles` (list of `ROLE_*`).
2. Later requests: the resource server decodes the JWT; `JwtAuthenticationConverter` reads `roles` with an **empty prefix** (values already carry `ROLE_`).
3. `CurrentUser` reads the `uid` claim from the `JwtAuthenticationToken`: use it for the acting user.
4. Login also returns an opaque **refresh token** (`RefreshTokenService`). `POST /api/v1/auth/refresh` rotates it: used token revoked, successor issued in the same `family_id`; replaying a revoked token revokes the whole family (reuse detection). `POST /api/v1/auth/logout` revokes the family; disabling or deleting a user revokes all their refresh tokens. Access tokens are stateless, valid until expiry (15 min).
5. Sign-up issues an **email verification token** (`EmailVerificationService`), emailed through the `mail` package; `POST /api/v1/auth/verify-email` consumes it, `POST /api/v1/auth/verify-email/resend` replaces it. Login does not require a verified email.
6. **Password reset** (`PasswordResetService`): `POST /api/v1/auth/password-reset/request` always answers 202, emailing a 1-hour single-use link only to enabled accounts, so it reveals no email's existence. `POST /api/v1/auth/password-reset/confirm` sets the password, revokes all refresh tokens, marks the email verified.

Refresh, verification and reset tokens: 256-bit random values (`OpaqueTokens`), only their SHA-256 hash stored. `ExpiredTokenPurgeJob` deletes them daily once expired for `identity.token-purge.retention` (7 days); refresh tokens by whole family, since reuse detection needs a revoked token while its family is usable (`ExpiredTokenQueries`).

7. **GDPR retention** (`UserRetentionService`, daily at 04:00 by `UserRetentionJob`, settings under `identity.retention`):
   - users soft-deleted for 30 days are erased in native SQL (`UserRetentionQueries`): profile becomes "Deleted user" without photo; `users` row deleted with roles, settings and tokens. Tasks and history keep pointing to the profile; the original email is free for a new sign-up. Photo files go with the media cleanup (same 30 days).
   - accounts inactive for 2 years get a warning email, are deleted 30 days later if still inactive, then anonymized by a later run. Activity: `last_active_at`, set by login and token refresh (`User.markActive`, which also clears the warning); older rows fall back to `last_login_at`, then `created_at`.
   - admins are never warned or deleted for inactivity, so the last admin cannot disappear.

Public endpoints: `POST /api/v1/users` (sign-up), `POST /api/v1/auth/login`, `/refresh`, `/logout`, `/verify-email`, `/password-reset/request`, `/password-reset/confirm`, identicons. Listed once in `identity.security.PublicEndpoints`: `SecurityConfiguration` permits them, API docs mark them public. They ignore the `Authorization` header: a client keeping its expired access token got a 401 from login and refresh.

### Rate limiting

`RateLimiter` limits endpoints anyone can call: login (per client address and per email), sign-up (per address), password reset request (per address and per email) and confirmation (per address, sharing the request's counter), verification email resend (per user), and webhook test events (per user: each is an HTTP call to a user-chosen URL). Fixed windows under `rate-limit.*`; over a limit, `RateLimitExceededException` -> 429 with `Retry-After` header.
- Counting: one atomic `INSERT ... ON CONFLICT ... RETURNING` on `rate_limit_counters` (`RateLimitQueries`): holds across instances without Redis. Each check commits in its own transaction (`REQUIRES_NEW`) before the request is handled, so a failed login still counts. A refused request rolls back its own increment, using no allowance (`RateLimitTests` locks this).
- The per-email reset limit counts every email, used by an account or not: a 429 reveals nothing about which emails exist.
- Keys (`RateLimitKeys`): addresses and emails SHA-256 hashed (fixed length, no personal data in clear; an email lengthened by lower-casing once overflowed the column and failed the request); an IPv6 address counts as its /64, which one client usually holds entirely.
- Window: 1 second to 1 day (`@DurationMin`/`@DurationMax`): a zero window divided by zero, and counters are purged after a day. `Retry-After` rounds up to the next whole second.
- Client address: `HttpServletRequest.getRemoteAddr()`. Behind a reverse proxy, set `server.forward-headers-strategy` (`FORWARD_HEADERS_STRATEGY`) to take it from `X-Forwarded-For`. Warning: never enable it without a proxy that overwrites that header, or clients choose their own address and escape the limits.
- Tests turn limits off (`rate-limit.enabled: false`), except `RateLimitTests`.

### Task access rules

Only **active** users (`UserStatus.ACTIVE`: enabled, not deleted, email verified) work on tasks.
- **Callers:** `ActiveUserAuthorizationManager` guards `/api/*/tasks/**`, `/api/*/notifications/**` and `/api/*/exports/**` in `SecurityConfiguration`, every API version included. It reloads the user per request: a disabled, deleted or unverified user gets 403 even with a valid access token. User and auth endpoints are not restricted to active users.
- **Assignees:** `TaskService` refuses a non-active assignee: `AssigneeNotActiveException` (422).
- **Responses:** task responses and history show referenced users as `UserProfileResponseDto(id, displayName, status, avatarUrl)`, `status` being `ACTIVE`, `UNVERIFIED`, `DISABLED` or `DELETED`.
- **Listing:** `GET /api/v1/tasks`, paginated, filters on `status`, `assigneeId`, `archived` (default false).
- **Pages:** every paginated list returns Spring Data's `PagedModel` (`{content, page: {size, number, totalElements, totalPages}}`), never a `Page`, whose JSON has no stable structure. `spring.data.web.pageable.max-page-size` clamps a page to 100 items.

### Task comments

`/api/v1/tasks/{id}/comments`: any active user posts (JSON `{"body"}`, or multipart with a `body` field and up to 5 `files`) and lists (paginated, oldest first). Only the author edits, admins included; author or admin deletes.
- **Files** posted with a comment are task attachments with `comment_id` set, so also in the task's attachment list; deleting the comment deletes them.
- **Mentions:** `<@user-id>` tokens in the body (`CommentMentions`), stored in `task_comment_mentions`, returned as `mentions`. A new mention must name an active user (`InvalidMentionException`, 422); an edit validates and notifies only users it mentions for the first time.
- **Emails:** mentioned users get a mention email; the assignee gets a comment email unless also mentioned with mention emails kept on.
- History events: `COMMENT_ADDED`, `COMMENT_EDITED`, `COMMENT_DELETED`; each file also records `ATTACHMENT_ADDED`/`ATTACHMENT_REMOVED`.

### Due-date reminders

`TaskReminderJob` runs `TaskReminderService.sendDueReminders` on `task.reminders.cron` (every 15 minutes): emails the assignee of each open task (not done, cancelled or archived) once when the due date is within `task.reminders.due-soon-lead-time` (24 h), and once after it passed, within `task.reminders.overdue-lookback` (7 days).
- `task_reminders` records what was sent, one row per task, kind, due date and recipient, by `INSERT ... ON CONFLICT DO NOTHING` (`TaskReminderQueries`). Moving the due date or reassigning makes a new reminder due.
- ShedLock-locked (see Scheduled jobs).
- Tests disable the job (`task.reminders.enabled: false`) and call the service with a fixed `Clock`.

### Users and their profile

One user = two rows sharing one UUID: **`users`** (`User`), the account (email, password, roles, verification, activation, activity), with `@SoftDelete`; **`user_profiles`** (`UserProfile`), what others see (display name, photo, status copy), no soft delete.
- **References:** every entity pointing to a user (tasks, history, comments, mentions, reminders, media, tokens) points to `UserProfile`, never `User`, set by `userProfileRepository.getReferenceById(id)` (proxy, no query). The profile outlives the account: a deleted user still loads, with status `DELETED`; an anonymized one stays "Deleted user" after its `users` row is gone.
- **Key direction:** `users.id` is the foreign key to `user_profiles.id` (`@MapsId`), never the reverse, so deleting the account leaves the profile. Creating a `User` creates its profile (cascade); `user.getDisplayName()` reads the profile.
- **Status:** `user_profiles.status` copies the account state, for display. `User` writes it on every transition (`setEnabled`, `setEmailVerifiedAt`, `markDeleted`); native SQL changing an account must update it too. Access checks (`ActiveUserAuthorizationManager`, assignees) read the account itself.
- **Photo:** `UserProfile.visibleAvatar()` hides the photo of a disabled account (file kept) or a deleted one; without a visible photo, `avatarUrl` is the identicon (see Media storage).
- The name avoids Spring Security's `UserDetails` interface.

Warning: do not map an association to `User` with `@NotFound(IGNORE)` to tolerate deleted users: Hibernate drops the foreign key from its model, and `liquibase:diff` proposes dropping the real constraints. That is how 7 foreign keys once went missing from the model.

Warning: Hibernate refuses a `LAZY` to-one association to an entity with `@SoftDelete` (`Task`, `User`), failing at session factory build, so only at startup. Map such associations `EAGER` (as `TaskAttachment.task`, `TaskEvent.task`), or point to an entity without `@SoftDelete` (as user references point to `UserProfile`).

### Loading data

`spring.jpa.open-in-view` is off: the persistence context closes with the service's transaction, before the controller writes the response. Reading an association nobody loaded fails with `LazyInitializationException` in tests instead of silently running one query per row.
- **To-one associations:** `@EntityGraph` on the repository methods feeding responses (tasks with users and photos, events with actor, comments with author, attachments with media and uploader, `UserRepository.findWithProfileById`).
- Warning: every graph is `type = EntityGraphType.LOAD`. The default, FETCH, makes every unlisted attribute LAZY, EAGER mappings included, which dropped the account's roles.
- **Collections and nested photos** (comment mentions and files): the service touches them before returning (`TaskCommentService.withDetailsLoaded`); `hibernate.default_batch_fetch_size: 50` then loads them for a whole page in a few `IN` queries.
- **Proxies** from `getReferenceById` (a new task's creator, a new comment's author): loaded with `ProfilesForDisplay.load` before the service returns them.
- Associations to users and media are LAZY; only those to `Task` (`@SoftDelete`) stay EAGER.
- Measured on a page of 20 tasks: 3 queries, whatever the number of distinct users (8 before, growing with them).
- `TaskQueryCountTests` and `UserQueryCountTests` lock these counts: a read runs as many statements for a long list as for a short one. `support.SqlStatementCounter`, a Hibernate `StatementInspector` registered in the test `application.yaml`, records only the test thread, since the outbox relay and listeners query on their own threads.

### Caching

Two Caffeine caches on Boot's cache manager, built by `CacheConfiguration`, listed in `spring.cache.cache-names` so a mistyped name fails instead of creating a cache without limit or metrics. Metrics per cache, on the management port: `cache.gets` (hit or miss), `cache.size`, `cache.evictions`.
- **`userStatus`** (`UserStatusLookup`): status `ActiveUserAuthorizationManager` checks on every task request, via light query `findAccountStateById`, kept `identity.status-cache.ttl` (30 s, 1 s to 1 min) after write.
  - `@Cacheable(sync = true)`: Caffeine loads under the key's lock, so an eviction during a load waits, then removes what it stored. Without it, a request reading ACTIVE just before a disable committed stored it after the eviction: access kept until TTL. Spring forbids `unless` with `sync`, so refused statuses are cached too.
  - Every account change publishes `AccountStateChanged`; `UserStatusCacheEviction` evicts after commit. Warning: any new way of changing an account, native SQL included, must publish it, or a disabled account keeps access until TTL. Spring Data's `@DomainEvents` would not fire: entities change by dirty checking, without `save()`.
  - Warning: never expire after access or refresh after write: a client looping keeps a stale ACTIVE alive; a refresh serves the old value when the database fails.
  - Other instances evict on the `AccountStatusChanged` broadcast (see Real-time events); until then, or while RabbitMQ is down, TTL is their delay. Write-time checks (assignee in `TaskService`) read the account, never the cache.
- **`mediaDownloads`** (`MediaService.downloadUrl`): presigned URL per media, so browsers get the same URL and reuse the file. Entry lives at most half the URL's validity, less when temporary AWS credentials end the URL sooner (`CacheConfiguration.reuseWindow`); URL signs `Cache-Control: private, max-age=<validity>, immutable`. Warning: `@Cacheable` sits on `MediaService`, not `MediaUrls`, whose `avatarOf` calls `of` on itself and would bypass the cache proxy.

### Mail

`io.julienmetral.tasks.mail`: cross-cutting. Features call `MailService.send(MailMessage)`, usually from an event listener writing the content (e.g. `identity.mail.VerificationEmailSender`). Sender: `mail.from`.
- **Queueing:** `MailService.send` writes via outbox (see Outbox) to durable queue `mail.send`, in the caller's transaction: rollback sends nothing, broker outage only delays.
- **Sending:** `MailQueueListener` sends via SMTP. Failures retry in the consumer with backoff (`spring.rabbitmq.listener.simple.retry`, about 1.5 minutes), then go to `mail.send.dead-letter`, kept for inspection or manual move in the RabbitMQ management UI (http://localhost:15672 in development). A never-buildable message is dead-lettered at once. At-least-once delivery.
- **Timeouts:** `spring.mail.properties` bounds SMTP connect (5 s), read and write (15 s), all profiles. Jakarta Mail otherwise waits for ever: a hung server holds a consumer without exception (no retry, no dead letter) and hangs the `mail` health check.

Development SMTP: Mailpit service of `compose.yaml` (UI http://localhost:8025). Tests start RabbitMQ and Mailpit containers (`TestcontainersConfiguration`), read emails with `support.Mailpit`; sending is asynchronous, so use its waiting methods (`latestTextTo`, `latestVerificationTokenFor`).

### Webhooks

HTTPS endpoints receiving a user's task notifications: `/api/v1/users/{id}/webhooks`, user or admin. README documents the receiver contract.
- **Secrets:** Standard Webhooks `whsec_`, 32 random bytes, AES-256-GCM encrypted by `WebhookSecrets` (`webhooks.encryption-key`, `WEBHOOK_ENCRYPTION_KEY`; prefix `v1:` names the key). Shown only in creation and rotation responses. Rotation keeps the previous one `webhooks.previous-secret-validity` (24 h) so receivers can switch, unless `WebhookSecrets.canDecrypt` finds it unreadable: then none kept, `previousSecretExpiresAt` null.
  - Warning: a new encryption key makes every stored secret and Slack URL unreadable. Each delivery then fails at once with `SecretUnreadable`: no request, not counted towards `failing_since` (like `EndpointDisabled`, `AccountNotActive`); a test event reports it. Owner recovers by rotating the secret or resending the Slack URL. Unreadable previous secrets are left out of signatures. Before, the exception dead-lettered the message and the retry job requeued it every 5 minutes for 30 days.
- **URLs:** on declare or change, `WebhookUrlPolicy` refuses non-HTTPS or port other than 443 (`webhooks.require-https=false` only on a development machine), credentials in the URL, hosts resolving to non-public addresses. The HTTP client rechecks at every call (see Outgoing HTTP): a public host can later resolve to an internal address.
- **Events:** `WebhookEvent`, one per `TaskNotificationType`, named `task.assigned` etc. in API and payloads.
- **Limits and erasure:** 5 endpoints per user (`webhooks.max-per-user`); creation locks the account row, so concurrent creations count each other. Account erasure deletes its endpoints (`UserRetentionQueries`).
- **Deliveries:** `WebhookNotificationSender` listens to `TaskNotificationCreated` in the publisher's transaction; endpoint events replace email switches. `WebhookDeliveryService.schedule` saves one `WebhookDelivery` per endpoint, queued via outbox (`webhook.deliver`); its id is every attempt's `webhook-id` header.
  - Attempt: read delivery, call receiver outside any transaction, record result, so a slow receiver never holds a DB connection. Payload stored as text, sent as those exact bytes, which the signature covers.
  - `WebhookClient`: HTTP service client (`@HttpExchange`, `@ImportHttpServices`, group `webhooks` under `spring.http.serviceclient.webhooks`: 5 s connect, 15 s read, no redirect, no cookie). Group configurer turns every status into a response; metrics and traces get a constant client name, no host or URL.
  - Retries in the database, not RabbitMQ: `next_attempt_at` after 5 s, 5 min, 30 min, 2 h, 5 h, 10 h (plus or minus 20 %, or a longer `Retry-After`), then FAILED. `WebhookRetryJob` claims due ones (`FOR UPDATE SKIP LOCKED`), pushes them to lease end (`webhooks.delivery-lease`) before queueing, so a crashed attempt comes due again. Listener has its own factory without retries: the global listener retry sleeps on the consumer thread.
  - 410 disables the endpoint (`GONE`). All attempts failing for `webhooks.disable-after` (3 days from `failing_since`, cleared by a success) disables it (`FAILING`) and emails the owner, host only.
  - **Slack:** kind `SLACK` accepts only `https://hooks.slack.com/services/` URLs (`WebhookUrlPolicy.checkSlack`: no destination to choose, nothing to resolve). The URL is its credential: stored encrypted by `WebhookSecrets`, shown as `WebhookUrls.SLACK_MASK`. Bodies: `SlackMessages`, unsigned. Slack's 403, 404, 410 disable it as `GONE`; its 400 fails the delivery without retries.
  - **Resilience:** `WebhookClient.send` has Spring 7 `@Retryable` (`@EnableResilientMethods` on `WebhookConfiguration`): one quick retry, only on connect failure, when the request cannot have reached the receiver. `WebhookResilience`: Resilience4j circuit breaker and bulkhead per receiving host, built in code (annotations cannot key by host); a delivery they refuse is postponed without using an attempt. State per instance, in memory; durable state stays in the database. Test events bypass them. Only aggregate gauge `webhook.circuit.breakers.open` is published: per-host series would grow with subscribers.
  - `POST .../test` sends `webhook.test` at once via the same client, records nothing; `POST .../deliveries/{deliveryId}/redeliver` restarts a delivery, same id. `WebhookDeliveryPurgeJob` deletes deliveries older than `webhooks.delivery-retention` (30 days): they hold names and comment excerpts.
  - Warning: never store or log a client exception message: it carries the URL, and a Slack URL its secret. `last_error` holds a short kind (`Timeout`, `ConnectionFailed`, `InvalidResponse`, `DestinationNotAllowed`, `HostUnavailable`, `EndpointDisabled`, `AccountNotActive`, `SecretUnreadable`).

### Real-time events

Events for connected clients reach every instance: listeners write them with `Outbox.broadcast` in the change's transaction; fanout exchange `tasks.realtime` copies each to one queue per instance (`RealtimeConfiguration`): exclusive, auto-delete, name known only to its instance, so an instance gets only what is published while it listens. `RealtimeListener` consumes on one thread, in order, no retries: a failed event is dropped, a stale one being worth less than those behind it.
- **Messages:** `UserNotification` (from `TaskNotificationCreated`); `TaskRoomEvent` (from `task.events.TaskEventRecorded`, published by `TaskEventService` per history row, and from `TaskDeleted`); `AccountStatusChanged` (from `AccountStateChanged`; also evicts the instance's cached status, closes the account's streams and sessions). Event id = outbox row id = AMQP message id, same on every instance.
- **Notification streams:** `GET /api/v1/notifications/stream` returns an `SseEmitter` (`realtime.sse.NotificationStreams`), ending at token expiry or after `realtime.streams.max-duration`; client reconnects with `Last-Event-ID`.
  - **Replay:** each instance keeps notifications it relayed for `replay-window` (`NotificationReplayBuffer`). Known id -> replay what followed; unknown id -> `resync` event, also sent to every stream after the instance's consumer restarts (its queue went with the connection).
  - **Writing:** per stream, a bounded buffer and a virtual-thread writer, so a slow client never holds up the listener; filling the buffer disconnects the client, which catches up by replay. A comment goes out after `heartbeat` of silence.
  - **Account changes:** opening a stream registers it, then reads the account, not the cache: a change committed after that read is broadcast, and `closeIfNoLongerActive` closes the stream on arrival. At most `max-per-user` streams per user and instance (429).
  - **Shutdown:** streams completed on `ContextClosedEvent`, else Tomcat's graceful shutdown waits for each until its timeout. Excluded from `http.server.requests` (`RealtimeConfiguration`); `SecurityConfiguration` permits the `ASYNC` dispatch ending it.
  - Warning: `SseEmitter.SseEventBuilder` is not reusable (`build()` appends to it): events wait as immutable `StreamEvent`s, built per write.
  - Warning: never interrupt a stream's writer to stop it: under Tomcat, a write by an interrupted thread closes the connection's (interruptible) NIO channel. `NotificationStream` wakes it with an event instead.
- **Task rooms:** STOMP over WebSocket on `/ws`, outside `/api/v{n}` (`realtime.stomp.StompConfiguration`). Clients subscribe to `/topic/tasks/{id}`; each instance's simple broker forwards room events it receives, broadcast id in an `event-id` header. Events say what happened, not the new state: clients reread the task via the API.
  - **Security:** handshake public (browsers send no header with it), ignores `Authorization`; the CONNECT frame carries the token. `StompAuthentication` decodes it with the API's `JwtDecoder`, reads the account (active only), strips the header before anything logs it, hands the session to `StompSessions`, which closes it (1008) at token expiry or once the account is not active. `MessageMatcherDelegatingAuthorizationManager` then allows CONNECT once authenticated and SUBSCRIBE to an existing task's room for an active account (`TaskRoomAuthorization`); refuses every frame sent to a destination. Allowed origins: `realtime.rooms.allowed-origins`, empty = the API's own.
  - Not `@EnableWebSocketSecurity`: its CSRF check on CONNECT cannot be turned off and protects cookie sessions, which this API lacks.
  - Warning: not `setPreserveReceiveOrder`: its decorator sends frames asynchronously and only logs what an interceptor throws; a refused CONNECT got no ERROR frame, stayed open without a user, and was logged at ERROR with its headers. Refusals answer an ERROR frame with the reason (`RefusalReasons`), then close.
  - Warning: `@EnableWebSocketMessageBroker` defines `messageBrokerTaskScheduler`, so Boot backs off from its own `taskScheduler`: every `@Scheduled` job silently ran on the broker's heartbeat pool. `StompConfiguration` redeclares `taskScheduler` as Boot does.
- Tests: RabbitMQ is never reused, so a context's broadcasts never reach another.

### Media storage

- **Uploads:** multipart through the API. `MediaService.store`: empty file 400; over the usage's limit 413 (`media.*-max-size`); real type detected from the bytes by Apache Tika, never from the client's `Content-Type` or extension; type outside `MediaUsage`'s list 415. Streamed to object storage under `<usage>/<uuid>` (never the client's file name) plus a `media` row with the SHA-256. Caller's transaction rolls back -> object deleted.
- **Antivirus:** after the type check, before storage, `MediaService` streams the file to ClamAV through `VirusScanner`; `ClamAvScanner` speaks clamd's INSTREAM protocol over TCP, no client library.
  - Infected: 422, never stored. clamd unreachable: 503, never stored unscanned (fail closed).
  - `antivirus.enabled=false` (`ANTIVIRUS_ENABLED`): a scanner accepting everything, warning logged at startup; for development machines that cannot spare ClamAV's memory (about 1 GB).
  - Tests: ClamAV container loading only an EICAR signature (`TestcontainersConfiguration`), about 14 MB instead of about 1 GB for the full database, freshclam disabled. The EICAR test string is the infected file, reported as `TestcontainersConfiguration.EICAR_THREAT`.
- **Profile photos:** `PUT /api/v1/users/{id}/avatar` (multipart field `file`) and `DELETE /api/v1/users/{id}/avatar`, user or admin, `AvatarService`.
  - **Upload (synchronous):** stores the file as uploaded (`MediaUsage.AVATAR_UPLOAD`: size, type, viruses), rejects images over 10000 px or 40 MP from the header alone (422), keeps it in `user_profiles.pending_avatar_media_id`, answers 202 with `avatarPending: true`. A newer upload replaces a pending one.
  - **Processing (worker):** same transaction writes the upload to the outbox for `avatar.process`; `AvatarProcessingListener` calls `AvatarService.process`: EXIF orientation, centred square crop, scale down to 256 px, re-encode to JPEG (PNG if the original has transparency), dropping all metadata, GPS included. Stored with `MediaService.storeGenerated` (`MediaUsage.AVATAR`), no type detection or second scan: the upload was scanned, the output is pixels the application re-encoded. Through `store`, clamd down during processing dead-lettered an already scanned photo. Replaces the current photo; the upload is deleted. Stale message (upload replaced or removed since): no-op. Undecodable image: dropped with a warning. Other failures: retried, then dead-lettered to `avatar.process.dead-letter`.
  - **Concurrency:** upload request and worker both lock the user row first (`UserRepository.findByIdForUpdate`); without that common lock they deadlocked. `User` and `UserProfile` are `@DynamicUpdate` (updates write only changed columns): the worker once rewrote the whole row and re-enabled an account an admin had disabled meanwhile.
  - Previous photo deleted with `MediaService.delete`: row with the change, object once the transaction commits.
  - `user_profiles.avatar_media_id` and `user_profiles.pending_avatar_media_id` have explicit unique constraints (`user_profiles_avatar_media_idUQ`, `user_profiles_pending_avatar_media_idUQ`). Associations are `@ManyToOne`: `@OneToOne` makes Hibernate add an implicit unique constraint with a generated name, which `liquibase:diff` then reports.
- **URLs in responses:** `UserResponseDto` and every `UserProfileResponseDto` carry `avatarUrl` from `MediaUrls.avatarOf`: presigned URL of the visible photo, else the profile's identicon. Controllers pass `MediaUrls` to the DTO constructors.
- **Identicons:** `GET /api/v1/identicons/{id}` (public: `<img>` tags send no token) returns an SVG coloured from the id alone (`IdenticonGenerator`): no database read, reveals nothing; cached a year (`Cache-Control: immutable`, `ETag`).
- **Cleanup:** `MediaCleanupJob` runs `MediaCleanupService` on `media.cleanup.cron` (default daily 03:30), locked (see Scheduled jobs). Native SQL (`MediaCleanupQueries`): JPA cannot see soft-deleted rows. Purges:
  - attachments of tasks, and profile photos of users, soft-deleted longer than `media.cleanup.retention` (30 days);
  - unreferenced media rows and stored objects without a media row, once older than `media.cleanup.orphan-grace-period` (1 day), sparing uploads in progress.
  - Rows go in one transaction, objects after the commit; an object that fails to delete is swept next run.
- **Downloads:** never through the application. `MediaService.downloadUrl` returns a presigned URL, valid `storage.presigned-url-ttl`, whose signed response headers force an attachment download under the original file name.
- **Drivers:** code depends on `ObjectStorage`; `storage.driver` picks the configuration.
  - `rustfs` (`RustFsStorageConfiguration`): explicit endpoint, static keys, path-style URLs, bucket created on startup. Development (RustFS service of `compose.yaml`, console http://localhost:9001) and tests (RustFS container in `TestcontainersConfiguration`).
  - `aws-s3` (`AwsS3StorageConfiguration`): endpoint from `storage.aws-s3.region`, credentials from the AWS default chain (environment variables, IAM role), bucket provisioned by the infrastructure. No integration tests.

  Both use `S3ObjectStorage`; a non-S3 driver needs only another `ObjectStorage` implementation. S3 failures -> `StorageUnavailableException` (503).
- **Server:** RustFS (S3-compatible) in development and tests, because MinIO no longer publishes Docker images.

### Outgoing HTTP

Every HTTP client Spring Boot builds (`RestClient.Builder` bean, HTTP service clients) goes through `config.OutboundHttpConfiguration`; the AWS SDK builds its own, unaffected.
- **Client:** Apache HttpClient 5, set explicitly (`spring.http.clients.imperative.factory: http-components`): otherwise it was picked only because the AWS SDK brings it. Warning: its automatic retries stay off: its default strategy re-sent a POST on 429 or 503, after sleeping for whatever `Retry-After` the server sent.
- **Addresses:** a Boot `InetAddressFilter` allows public addresses only, plus the CIDR ranges of `outbound-http.allowed-addresses` (`OUTBOUND_HTTP_ALLOWED_ADDRESSES`, empty in production). Apache connects to exactly the addresses the filter checked, so DNS rebinding cannot bypass it. Refused host -> `FilteredHostException`, unwrapped by RestClient. Three IPv6 ranges embedding an IPv4 address are also refused, because `externalAddresses()` lets them through.
- Warning: never set the `http.proxyHost` or `https.proxyHost` system properties: Boot builds the Apache client with `useSystemProperties()`, and behind a proxy the filter checks the proxy's address, not the target's.
- **Timeouts:** 5 s connect, 15 s read by default (`spring.http.clients.*`); Apache's defaults wait minutes for a connection.
- **Tests:** a local test server needs `127.0.0.1/32` in the allowed ranges. Use MockWebServer (`mockwebserver3`): it runs the real client, filter and timeouts; `MockRestServiceServer` replaces the client and tests none of them.

### Outbox

Every RabbitMQ message goes via `messaging.services.Outbox.enqueue` (queue) or `Outbox.broadcast` (exchange reaching every instance), never `RabbitTemplate` directly. It writes an `outbox_messages` row in the caller's transaction (`Propagation.MANDATORY`): the message exists if and only if the business change commits.
- `OutboxRelay.publishNow` publishes right after the commit, on an `@Async` thread. Before setting `published_at` it waits for the broker's confirm (`spring.rabbitmq.publisher-confirm-type: correlated`) and checks the (mandatory) message was not returned unroutable: RabbitMQ also confirms a message for a missing queue.
- Failed publish -> `attempts`, `last_error`, `next_attempt_at` (5 s, doubling, capped at `messaging.outbox.max-retry-delay`). `OutboxRelayJob` retries due messages every `messaging.outbox.poll-interval`; `OutboxPurgeJob` deletes published ones after `messaging.outbox.retention`.
- Rows locked `FOR UPDATE SKIP LOCKED`: immediate publish, poller and other instances never send the same message twice at once. A crash between confirm and commit publishes again: at-least-once delivery, consumers must tolerate duplicates.
- Class name in the `__TypeId__` header; the converter in `MessagingConfiguration` must trust the class's package.
- A broadcast no queue receives is marked published: no instance listens, nobody to reach.

### Exports

`POST /api/v1/exports/tasks` (any active account, task list filters) and `POST /api/v1/exports/users` (admins) answer 202 with the export and its `Location`; `GET /api/v1/exports[/{id}]` and `DELETE /api/v1/exports/{id}` see only the caller's exports (404 otherwise). At most one export per type queued or running per owner (`export-in-progress`, 409); the request locks the owner's account row, so two at once count each other.
- **Flow:** `DataExportService.request` saves a `data_exports` row (QUEUED), queues `export.run` through the outbox. `DataExportRunner`, on the listener's thread, claims it (QUEUED to RUNNING with a lease, conditional `UPDATE`: a duplicate message does nothing) and starts its job with `JobOperator` outside any transaction: Batch refuses to start inside one. Listener: one export at a time, no retries, acknowledges once the job ended.
- **Jobs** (`export.batch.CsvExportJobs`): a chunk step pages rows with `JdbcPagingItemReader` into a local file (`FlatFileItemWriter`), then a tasklet (`PublishExport`) stores it as a media (`MediaService.storeGenerated`, no type detection or scan: the application wrote it), marks the export COMPLETED, emails the owner after the commit. `DataExportJobListener` deletes the local file, records a failed run (FAILED, exception's class, never its message).
  - Only job parameter: the export's id; filters are read from the row, so no personal data lands in Batch's tables.
  - Readers page by id (UUIDv7) over their query made a subquery, `PostgresPagingQueryProvider` given: detecting it reads the database's metadata. Native SQL sees soft-deleted rows: each query writes `deleted_at IS NULL`.
  - `CsvLineAggregator` quotes every value and neutralises formulas (OWASP CSV injection); Batch's `DelimitedLineAggregator` neither quotes nor escapes. The header callback writes a UTF-8 byte order mark for Excel.
- **Personal data** (`POST /api/v1/exports/my-data`, `batch.PersonalDataJob`): three tasklet steps, each reading the previous one's output:
  - `my-data.json` (complete, `version` for its format) from `PersonalDataQueries` (native SQL: the account's soft-deleted tasks are its data too; others by display name only; no secret; Slack URL masked);
  - `my-data.pdf` from it, by `PersonalDataPdf` (plain Thymeleaf `TemplateEngine` in XML mode, `templates/exports/personal-data.xhtml`, rendered by openhtmltopdf);
  - a ZIP with the profile photo.
  - A run's files live in `ExportFiles`' directory of the export, deleted when the job ends.
  - Warning: the PDF renderer refuses every external resource (`useExternalResourceAccessControl`, before and after resolving), or the server would fetch any URL a template referenced. Values via `th:text` only, never `th:utext`.
  - Noto Sans embedded (`fonts/`, OFL licence): PDF standard fonts cover Western European letters only.
- **Interrupted runs:** `DataExportRecoveryJob` re-queues, up to `exports.max-attempts`, a RUNNING export whose lease ran out. `DataExportRunner` then recovers its Batch execution left STARTED (`JobOperator.recover`), and the job instance restarts; both steps rerun (`allowStartIfComplete`), since the file stayed on the instance that stopped.
- **Retention:** `DataExportPurgeJob` deletes files past `exports.retention` (7 days; row stays as EXPIRED), then expired and failed exports and Batch executions older than `history-retention` (`BatchMetadataQueries`: Batch never deletes its history). The media cleanup spares media an export points to.
- **Batch setup:** `spring-boot-starter-batch-jdbc`; `spring.batch.job.enabled=false` (jobs start on request only); schema from Liquibase (changeset 023, a copy of Batch 6's `schema-postgresql.sql`, excluded from `liquibase:diff` in `pom.xml`); executions created at read committed: serializable failed concurrent starts on Postgres.
- Warning: Batch's JDBC repository reads database metadata during context refresh, which would fail the image's AOT training run: the `Dockerfile` excludes `BatchJdbcAutoConfiguration` there, and Batch uses its in-memory repository for the training only.
- Warning: `@SpringBatchTest` adds a context customizer, hence another context and RabbitMQ; build `JobOperatorTestUtils` from the beans instead. Never call `JobRepositoryTestUtils.removeJobExecutions()`: every context shares the Batch tables.

### Scheduled jobs

Jobs run with `@Scheduled` inside the API. One that must run once per schedule carries ShedLock's `@SchedulerLock` (`config.SchedulerLockConfiguration`): the method first takes its row in `scheduler_locks`; an instance finding it taken skips the run.
- **Locked:** media cleanup, user retention, due-date reminders, export recovery, and purges of outbox, rate limit counters, webhook deliveries, exports and expired tokens. Lock names: constants of `ScheduledJobLocks`.
- **Not locked on purpose:** outbox poller and webhook retries: every instance polls and `FOR UPDATE SKIP LOCKED` shares the backlog; a lock would leave it to one instance.
- **Switches:** every job but the outbox poller can be turned off per instance by a property (`@ConditionalOnBooleanProperty(..., matchIfMissing = true)` on its class, e.g. `rate-limit.purge-enabled`, `messaging.outbox.purge-enabled`), bound in its feature's properties record. The condition removes the whole bean, so each job has its own class: the outbox purge is `OutboxPurgeJob`, apart from the `OutboxRelayJob` poller.
- **Durations:** `lockAtMostFor` releases a crashed instance's lock: well above the longest run, below the period of a frequent job. `lockAtLeastFor` holds a quick run's lock a while, so an instance whose clock fires late does not rerun the job.
- **Times:** `usingDbTime()` takes every time from the database clock. Columns have no time zone on purpose: ShedLock writes UTC wall-clock values, which a `timestamptz` column would read in each session's zone.
- **A new job** needs a name in `ScheduledJobLocks` (its metrics are registered at startup) or a place on the pollers' allowlist, else `ScheduledJobLocksTest` fails.
- Replaced three hand-written advisory locks: held only while their transaction ran, they let an instance firing a moment later rerun the job.
- Warning: `@SchedulerLock` goes on the job method, never on a `@Transactional` one: the lock is written in its own transaction and would be released before the work commits. The method must be public.
- Warning: never delete a `scheduler_locks` row to free a stuck lock: ShedLock remembers rows it inserted and then only updates them, so every later run is skipped until a restart. Set `lock_until` to the current UTC time instead, `timezone('utc', now())` (README, Background work).

### Monitoring

Actuator has its own port, `management.server.port` (`MANAGEMENT_PORT`, 8081): `health`, `info`, `metrics`, `prometheus`, `sbom` exposed, no authentication. Warning: keep that port reachable only from the monitoring network.
- **API port:** no `/actuator/**`; `/livez` and `/readyz` serve the `livez` and `readyz` groups (members of `liveness` and `readiness`) without details, permitted in `SecurityConfiguration`, bearer token ignored. Reason: a probe on the management port alone could pass while the API port is down. Warning: not `add-additional-paths`: it reuses the probe groups, whose settings apply to all their paths; hiding details on 8080 hid them on 8081.
- `SecurityConfiguration` permits every request arriving on the management port (`local.management.port`), error page included: matching only the endpoints once made every error there answer 401.
- **Health:** Boot's `db`, `rabbit`, `mail`, `diskSpace`, plus `storage` (`StorageHealthIndicator`, `headBucket`) and `antivirus` (`AntivirusHealthIndicator`, clamd `PING` capped at 5 s; up with `scanning: disabled` when antivirus is off). Readiness (`/actuator/health/readiness`) has only `db`: RabbitMQ down only delays messages (outbox keeps them), storage or antivirus down only blocks files, so they must not take the API out of the load balancer.
- **Metrics:** `webhook.deliveries` per outcome, `webhook.circuit.breakers.open`; `outbox.messages.pending`, `outbox.messages.oldest.pending.age` (`OutboxMetrics`); `outbox.messages.published`, `outbox.publish.failures` per queue (`OutboxRelay`); `rabbitmq.dead.letter.messages` per dead-letter queue (`DeadLetterQueueMetrics`, NaN while the broker is unreachable); `notification.streams.open` per instance. Spring records every `@Scheduled` run, lock-skipped included, as `tasks.scheduled.execution`. ShedLock, per `lock_name`: counts `shedlock.lock.attempts`, `shedlock.lock.acquired`, `shedlock.lock.not.acquired`; times `shedlock.execution.duration`.
- **Info:** `spring-boot-maven-plugin` writes `build-info` (version in `/actuator/info`); `cyclonedx-maven-plugin` (configured by the Boot parent) writes the SBOM at `/actuator/sbom/application`.

### Deployment profile and image

Default configuration = development and tests. `application-prod.yaml` is the only other profile, for every deployed environment, staging included; environments differ by variables alone (README, Deploy the API). Do not add a profile per environment.
- **Setting without a safe production default:** empty default there (`${MAIL_HOST:}`) plus an entry in `deployment.required-properties`; `RequiredPropertiesCheck` stops startup before any bean is created, naming every missing setting. A localhost default would let a deployment start against nothing.
- Warning: never set `spring.profiles.active` in a file packaged in the jar, nor export `SPRING_PROFILES_ACTIVE` in a shell or IDE: tests would load `prod` over `src/test/resources/config/application.yaml` and stop on missing settings.
- **Image** (`Dockerfile`): jar built by Maven in a JDK stage, split by `jarmode=tools extract --layers`, run on the Temurin 25 JRE as uid 10001, `prod` profile set after the AOT training. Base images pinned by digest. `.dockerignore` is an allowlist: add any file the build needs.
- **AOT cache:** a build-time training run (`-XX:AOTCacheOutput`, `-Dspring.context.exit=onRefresh`) records classes loaded up to context refresh; startup then takes about a third less time (median of five alternating starts: 8.1 s instead of 12.8 s). Training reaches no service: Liquibase and Hibernate's JDBC metadata access off, explicit dialect. Warning: the image build fails on a bean connecting to a service during context refresh instead of in an `ApplicationRunner` or lifecycle `start` (Spring Batch's JDBC repository does, hence its exclusion from training), and on a new required startup setting until the training `RUN` gets a throwaway value (as `JWT_SECRET` and `WEBHOOK_ENCRYPTION_KEY` have).
- **`compose.production.yaml`** runs the image hardened, on its own copy of the services, as project `tasks-prod` (README, Run the production image locally).

### Method-security annotations

Authorization = custom meta-annotations wrapping `@PreAuthorize`, no inline SpEL. `AnnotationTemplateExpressionDefaults` is registered so `{value}` placeholders resolve; `UserRole` implements `ExpressionTemplateValueProvider`, so enum values render as quoted role names.

- `@AdminOnly`: role check.
- `@AllowedRolesOrSelfOnly(...)`: bean `userAuthorization` (`UserAuthorization`).
- `@AllowedRolesOrAssignedToOnly(...)` (`task.security`): bean `taskAuthorization` (`TaskAuthorization`).
- `@AllowedRolesOrUploaderOnly(...)`, `@CommentAuthorOnly`, `@AllowedRolesOrCommentAuthorOnly(...)` (`task.security`): beans `taskAttachmentAuthorization`, `taskCommentAuthorization`; read `#attachmentId` or `#commentId` instead.
- `@AllowedRolesOrWithoutAssigneeOnly(...)` (`task.security`): anyone creates an unassigned task; assigning on creation needs a role. Reads `#dto`.
- Each carries `@AccessDescription`, the rule's sentence in the API documentation. Warning: a rule without it, or `@PreAuthorize` directly on a controller method, fails `AccessDescriptionTest`.

The other annotations' SpEL reads parameter **`#id`**: annotated controller methods must name their path variable `id`. New ownership rule: a `@Component("name")` bean with a boolean method, plus a meta-annotation.

### Task event log

Every task mutation in `TaskService` must call the matching `TaskEventService` method (`created`, `updated`, `statusChanged`, `assignmentChanged`, `archived`, `cancelled`, ...). They are `@Transactional(propagation = MANDATORY)` (throw outside the caller's transaction) and write a `TaskEvent` row: current user as actor, type-specific payload record in a `jsonb` column. History: `GET /api/v1/tasks/{taskId}/events`.

`Task` uses optimistic locking (`@Version`). Mutations rely on JPA dirty checking in the transaction, no explicit `save()`.

### API documentation

springdoc serves OpenAPI 3.1 at `/v3/api-docs`, Swagger UI at `/swagger-ui.html` (`API_DOCS_ENABLED`, `SWAGGER_UI_ENABLED`, both off under `prod`). `docs/openapi.json` is a committed copy: `OpenApiSpecTests` fails when it differs from what is served; `./mvnw test -Dtest=OpenApiSpecTests -Dopenapi.update=true` rewrites it. CI: Spectral lints it, oasdiff fails a breaking pull request. `.oasdiff.yaml` lowers one rule: a value added to a response enumeration is compatible (the API description asks clients to accept unknown values); removing one still fails.
- **A new endpoint** needs: the controller's `@Tag`; `@Operation(summary)`; a method name unique across controllers (it is the operationId: `createTask`, `listTasks`); `@ResponseStatus` for 201, 202 or 204 (201 also gets a Location header); `@DocumentedProblems` for its typed problems; `@RateLimited` if it calls `RateLimiter`; if public, an entry in `PublicEndpoints`.
- **Versioned paths:** springdoc publishes the raw `/api/v{version}` prefix of a mapping without `version` attribute; `PathDocumentation` pins them to `/api/v1` before its other rules, which would read `{version}` as a resource id.
- **Added automatically** (`config.OperationDocumentation`, `config.PathDocumentation`, `config.NullabilityDocumentation`): bearer requirement or its absence, 401, 403 of an access rule and of task operations, 400 on input, 404 on a path naming a resource, upload problems, 429, a default response, the page size limit, required and nullable fields.
- **Nullness in the contract:** `NullabilityDocumentation` finds each schema's record by simple name and reads JSpecify `@Nullable` (TYPE_USE, which springdoc does not see). A `@Nullable` component allows `null` (a reference becomes `oneOf` it and `null`); a request requires every other component; a response requires every component, since Jackson writes nulls. A record with `@JsonInclude` other than `ALWAYS` keeps its null components optional, never `null`. Warning: adding or removing `@Nullable` on a DTO component changes the API contract (oasdiff judges it); a schema shared by a request and a response must have no `@Nullable` component, or building the document fails.
- Warning: `@ApiResponse` on a method without `@ResponseStatus` makes springdoc drop the success response; declare it too (see `AuthController.login`).
- Warning: the `Problem` schema is hand-written (`config.ProblemDocumentation`): springdoc's, derived from `ProblemDetail`, describes a `properties` object the JSON flattens. `springdoc.override-with-generic-response` stays false, or every `ApiExceptionHandler` handler becomes a response of every operation.
- `springdoc.allowed-locales` stays `en`: before springdoc 3.1.1, varying `Accept-Language` exhausted memory, one cached document per language.

### Errors

Every error is an RFC 9457 problem (`application/problem+json`), documented for clients in `docs/problems.md`. Domain exceptions live in each feature's `exceptions` package, mapped in `shared/exceptions/ApiExceptionHandler`; a new exception type without a handler there surfaces as 500.
- **Typed or not:** a domain rule the client can act on gets a `ProblemType` (type URI into `docs/problems.md`, constant title) and a section there. A generic HTTP condition (not found, unauthorized, too large, rate limited, unavailable) stays `about:blank`: leave `title` unset, Spring fills the status phrase, as the RFC asks. Warning: type URI and title are a client contract; renaming one is a breaking change.
- **Invalid input** (Bean Validation, wrong-typed value in body or parameter, missing parameter or part) -> `validation-error` whose `errors` list `{detail, pointer}` for the JSON body, else `{detail, parameter}` (`InvalidValue`). Parser and Java type names never reach the client.
- The handler extends `ResponseEntityExceptionHandler` for Spring MVC exceptions; their details are reworded in `messages.properties` (`problemDetail.<exception class>`). Warning: an `@ExceptionHandler` for an exception `ResponseEntityExceptionHandler` already handles (e.g. `MaxUploadSizeExceededException`) makes the mapping ambiguous and fails startup: override its method instead.
- Bean Validation messages follow `Accept-Language`; tests assert on `pointer` and `parameter`, or pin the language.
- Unexpected exception: logged, answered as a bare 500 problem (`handleUnexpected`), its message never in the detail. Warning: method security throws `AccessDeniedException` inside the controller call, so that handler rethrows it; catching it turns every 403 into 500.
- Security filters' 401 and 403 come from Spring Security, without problem body.

## Nullness

Every main package is `@NullMarked` (`package-info.java`, checked by `NullMarkedPackagesTest`): a type is "never null" unless it carries JSpecify's `@Nullable` (`@Nullable Instant`, `List<@Nullable UUID>`). NullAway (Error Prone, inside `./mvnw compile`) fails the build on a possible null dereference, a null passed or returned where none is declared, and an override narrowing a Spring signature (Spring 7 is JSpecify-annotated).
- Mark `@Nullable` what really can be null: entity fields on nullable columns (Lombok copies it to getters and setters), response components absent from some responses, optional parameters, lookups returning null. Entities are exempt from constructor initialization (`ExternalInitAnnotations`): Hibernate fills them.
- Non-null value NullAway cannot see: make it visible (early return, local variable) or `Objects.requireNonNull(value, "why")`; `@SuppressWarnings("NullAway")` only as last resort, with the reason.
- Unannotated libraries (Hibernate, AWS SDK, Tika) are trusted as non-null; when their documentation says a method can return null, keep the result in a `@Nullable` local and test it.
- Warning: `JdbcTemplate.queryForList(sql, params, X.class)` returns `List<@Nullable X>`; for a NOT NULL column use `query(sql, params, (row, n) -> row.getObject(1, X.class))`.
- Tests are not checked. Error Prone needs the `jdk.compiler` exports of `.mvn/jvm.config`, which `.dockerignore` lets into the image build with `lombok.config` (the image build failed without them); compiling takes a few seconds more.

## Comments and Javadoc: the why and the failure, never the what

**Name first, comment second.** A precise name removes the paragraph above it; a long name is the cheap side of that trade. `revokeAllForUser`, `existsByEmailIncludingDeleted` and `ActiveUserAuthorizationManager` need no gloss; `process`, `handle` or `check` plus three lines of explanation is the wrong trade. Comment only what a name cannot carry.

**Javadoc is not owed to every public type or method.** Controllers, DTOs, entities, repositories and self-describing one-line methods get none. Write it only when the signature cannot give the context: where the method sits in a flow, what must be true before calling it, side effects the signature hides (revoking sessions, publishing an event, sending an email after commit). `@param id the id` or `@return the user` is noise. Exception: configuration property records get one `@param` per property, since it documents the YAML key.

**A comment earns its place by saying what the code cannot**: would a reader with the code in front of them learn something they could not derive?

Keep:
- **A measured failure**: what went wrong and what it cost; these lines stop a defect from coming back. E.g. on `RefreshTokenRepository.revokeAllForUser`: "Native on purpose: in JPQL, `t.user.id` joins users, which `@SoftDelete` filters, so nothing would be revoked once the user is deleted".
- **A constraint not visible locally** (framework or library behaviour the code depends on): why `NotificationSettings.defaults` leaves the id null (`@MapsId`, and Spring Data's `merge` instead of `persist`), why `AuthService.refresh` needs `noRollbackFor`.
- **A decision and its reason** when the code shows only the outcome: why opaque tokens use SHA-256 rather than Argon2.
- **A trap**, starting with `Warning:`, where the obvious change is wrong: the warning on `User.profile` about the direction of the foreign key.

Cut:
- What restates the code (`// save the user` above `userRepository.save(user)`) or an annotation (`// transactional` above `@Transactional`, `// getters and setters` above `@Getter @Setter`).
- Narration of a service method's steps, and explanations of a well-named method: naming it well is the comment.
- A second copy of something in this file, an ADR or a PR description: link to it.

**No symbols or emojis.** Comments, Javadoc and documentation use plain words: no warning signs, light bulbs, check marks or any other emoji or pictograph. Mark a trap with `Warning:`, a side remark with `Note:`.

**Tests document themselves through their names** (`deletingUserRevokesRefreshTokens`, `signUpWithEmailOfSoftDeletedUserReturnsConflict`). A test comment explains only a non-obvious setup, such as waiting for the asynchronous mail dispatch.

**Rough ceiling, a smell rather than a limit:** with comments over about a quarter of a file, ask whether the code itself is unclear.

**Warning: this is not a licence to delete reasons.** The rule fights verbosity; the failure it could create is losing the one paragraph that stopped someone from reintroducing a defect. When a comment is long because it records something expensive, shorten the prose and keep the fact. When in doubt, keep it, tighter.

**Apply it opportunistically.** You may trim any file you read or modify while its context is loaded: the only way a convention reaches code written before it.

## Testing

- **Unit tests** (`*Test`): services and security components in isolation; JUnit 5, Mockito (`@ExtendWith(MockitoExtension.class)`), AssertJ; same package as the class under test.
- **Integration tests** (`*Tests`, `@IntegrationTest` in `support`): `@SpringBootTest`, MockMvc, `TestcontainersConfiguration` containers (Postgres via `@ServiceConnection`, so Liquibase runs on a real database), `Mailpit`, `TestClock`.
  - Most authenticate with the `jwt()` post-processor, a `uid` claim and a `ROLE_*` authority. The acting user must exist in the database: `TaskEventService` loads it.
  - `AuthControllerTests` sends real `Authorization: Bearer` tokens from the login endpoint.
  - **Time:** `TestClock` is the application's `Clock`: system time until a test pins it (`set`) or moves it (`advance`); reset after every test.
  - Production code reads time from the injected `Clock` (`clock.instant()`), never `Instant.now()`, so a pinned `TestClock` also dates tokens, tasks, comments and media. Unit tests pass `Clock.fixed`; with `@InjectMocks`, use a `@Spy` `Clock` field, or Mockito passes null. Exceptions: `JwtService` stays on system time, because the decoder's `JwtTimestampValidator` checks `exp` against the system clock; Spring Data auditing (`created_at`/`updated_at` of `AuditableEntity`) keeps system time on purpose: when dated by the `Clock`, tasks that `TaskReminderTests` created with a clock pinned in 2100 sorted first in every newest-first list of the shared test database, and three list tests failed (closed PR #79).
- **Web tests** (`*WebMvcTests`, `@WebLayerTest` in `support`): every controller and `ApiExceptionHandler` behind the real `SecurityConfiguration`, JWT decoding and method security, no Docker. Services, repositories and ownership beans that query the database are mocks. They cover request validation, 401, role-only 403, the ids SpEL passes to ownership beans, exception mapping; anything depending on stored data stays in `@IntegrationTest`.
  - Callers from `WebCallers` (`user`, `admin`, `withoutUid`); task endpoints need `WebCallers.everyAccountIsActive(userRepository)`, since `ActiveUserAuthorizationManager` reads the account status (`findAccountStateById`) through `UserStatusLookup`. `verifyNoInteractions(service)` proves a request was refused before the service ran.
- **SQL and repository tests:** slices on the same reused Postgres, migrated by Liquibase, rolled back after each test: `@JdbcSliceTest` (`JdbcTemplate`, every `*Queries` class) and `@RepositoryTest` (JPA, repositories, `TestEntityManager`, auditing). No `@AutoConfigureTestDatabase(replace = NONE)` needed: the default keeps a `@ServiceConnection` data source.
  - A test that must commit (locks seen from another connection, concurrency, Liquibase on its own connection) uses `Transactions.inNewTransaction` or `@Transactional(propagation = NOT_SUPPORTED)` and cleans up after itself. Fixtures of queries sweeping a whole table are dated in 2000, so cutoffs reach only the class's own rows.
  - Warning: Postgres is declared once, in `PostgresTestcontainersConfiguration`. Testcontainers reuses a container only when its whole definition matches; a second definition starts a second database.
- **Contexts:** Spring caches one context per distinct test configuration; each integration context starts its own RabbitMQ (and all its containers when reuse is off). Warning: a property, mock or import added to one class creates another context; use the annotations above alone unless the test cannot work otherwise. Integration contexts that differ on purpose: `@DeadLetterIntegrationTest` (fast retries, SMTP mock, storage and antivirus spies), `OutboxBrokerFailureTests` (template spy), `RateLimitTests` (limits on), `MonitoringTests` and `PublicEndpointErrorTests` (real server port). Slices add three light contexts: web, JDBC, JPA.
- **Shared data:** Postgres, Mailpit, RustFS and ClamAV are reusable containers; with reuse on (see the README), one of each serves every context and run. Unique emails and references (random UUIDs) in every test; never assert on global counts.
  - Warning: a background job enabled in a test context acts on every other context's data, and its lock in `scheduler_locks` skips the same job everywhere else. Tests keep scheduled jobs off and call the services directly, except the hourly outbox and rate limit purges, which only delete rows a day old or more (`ScheduledJobLockingTests` needs `RateLimitCleanupJob`). The outbox poller runs hourly (`messaging.outbox.poll-interval`): it would publish another context's messages to its own broker.
  - RabbitMQ is never reused: the dead-letter tests make listeners' collaborators fail, and on a shared broker those listeners would consume every other context's messages.
- `src/test/resources/spring.properties` caps the context cache at 12; an evicted context stops its containers, restarted when a later class needs it. Warning: a full run needs several GB of memory; never run two full suites at once on one machine.
- **Context pausing is off** (`spring.test.context.cache.pause=never`): Spring 7 pauses a cached context on every context switch, and each RabbitMQ listener container then waits for its consumers' 1 s receive timeout (22.5 s per CI run). Every context has its own broker, so a running cached context consumes nothing of another.
- **Waiting:** `support.AwaitilityDefaults` (a JUnit launcher session listener) sets Awaitility's default poll delay to zero and its poll interval to 20 ms, since the library reads no system property and its first check came after 100 ms. `Mailpit` polls every 20 ms too. Warning: a test that sets its own `pollInterval` or `pollDelay` keeps it.

## Git workflow and CI

- **Branches:** `features/<name>` -> PR to `develop` -> `release/<version>`, tagged `v<version>` -> merged to `main` -> merged back to `develop`.
- **Commits:** small; never mix production code and its tests in one commit. Conventional Commits prefixes (`feat`, `fix`, `test`, `build`, `ci`, `docs`, `chore`), in English.
- **Pull requests:** plain text only in titles and descriptions, like commits: no emojis or symbols. Size the description to the change: for a small or routine change, one or two sentences of context and a bullet list of what was done suffice. Sections such as a test plan or design notes only when the change needs them.
- **CI** (`.github/workflows/ci.yml`): `./mvnw verify` (tests + JaCoCo report artifact), gitleaks secret scan, API contract checks, image build and Grype scan. Runs on pushes to those branches, `v*` tags, and PRs to `develop`/`main`. Actions pinned to commit SHAs.
  - **Image scan:** a high or critical vulnerability with a fix fails the job; findings go to the Security tab. A fix Spring Boot does not ship yet = a version property override in `pom.xml`, with the reason and when to remove it.
  - **Release:** on a `v*` tag, once tests and scan pass, `publish` pushes the image to `ghcr.io` with BuildKit provenance and SBOM, plus a signed attestation (`actions/attest`).
  - **Dependabot** (`.github/dependabot.yml`): weekly pull requests to `develop` for Maven, the Dockerfile, `compose.yaml` and the actions.
- **Secret scanning:** run `gitleaks git . --redact` locally before pushing (gitleaks installed through mise).
